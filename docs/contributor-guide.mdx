# Documentation Standards

:::info[Audience]
This page is for anyone evaluating the documentation standards behind
this sample, including hiring managers and other technical writers.
:::

This guide states the rules behind the [Meridian Contract Logistics
sample](/docs/meridian-logistics/about-this-sample) and why each rule
exists. The goal is a system a team could run without me in the room.

## One Diataxis type per page

Every page in the sample is exactly one type. A page never mixes types.
The four types are:

- Explanation pages explain ideas.
- How-to guides show the steps for one task.
- Reference pages define terms and list facts.
- SOPs give a fixed procedure a team repeats exactly.

Mixing types hides key details. A step buried inside a concept page gets
skipped. A definition buried inside a how-to guide gets missed. Splitting
by type lets a reader trust what a page holds before they open it.

## A frontmatter schema that tooling can read

Every page in the sample carries this frontmatter:

```yaml
---
title: "..."
description: "..."
sidebar_position: N
doc_type: explanation | how-to | reference | sop
audience: "Warehouse Operations, Client Services"
owner: "Warehouse Operations Manager"
last_reviewed: YYYY-MM-DD
review_cadence: Quarterly | Biannual
applies_to: "All Meridian fulfillment sites"
---
```

Owner and review cadence live in frontmatter, not just in prose. A real
team can query that data later:

- Which pages are overdue for review
- Which team owns a given SOP
- Which pages a new hire should read first

A sentence buried in the page body cannot answer those questions.
Frontmatter can.

## Named ownership, never a named person

Every page names an owner role, such as "Warehouse Operations Manager."
No page names a person.

People change jobs. A role survives a reorg. Documentation naming a
person goes stale once that person leaves. Documentation naming a role
stays accurate as long as the org chart does.

## Audience labeling on every page

Every non-SOP page opens with an admonition. It states who the page is
for:

```
:::info[Audience]
This page is for Warehouse Operations and Client Services teams.
:::
```

SOPs skip this admonition. They state audience through the **Applies to**
line instead. That keeps the fact from appearing twice on the same page.

## One template for every SOP, no exceptions

Every SOP in this sample follows this exact structure:

```markdown
# SOP-XXX: [Title]

**Owner:** [Role, never a person's name]
**Last reviewed:** [Date]
**Review cadence:** [Quarterly / Biannual]
**Applies to:** [Which teams or sites]

## Purpose
## Prerequisites
## Procedure
## Troubleshooting
## Related documents
```

**Owner**, **Last reviewed**, **Review cadence**, and **Applies to** appear
twice: once in frontmatter, once as bold text in the body. That duplication
is deliberate, for two reasons:

- Frontmatter is what tooling reads.
- The bold text is what a person reads on the floor, not buried in page
  metadata.

A fixed template removes a decision. A new SOP author never has to invent
a structure. It also helps an audit: anyone can scan ten SOPs and know
exactly where the prerequisites or the troubleshooting steps sit.

## Procedural conventions

Numbered steps in a how-to guide or an SOP's Procedure section follow
three rules:

- One action per step.
- State the expected outcome when it is not obvious, so the reader knows
  the step worked before moving on.
- Place a warning immediately before the step it applies to, never
  after. A warning that arrives after the step is too late to prevent
  the mistake.

## No orphan pages

Every page must:

- Sit in the sidebar. Docusaurus builds it automatically from this
  site's folder structure.
- Link to at least one related page.

Cross-type links do more work than same-type links. A how-to page can
link to its matching SOP and to a glossary term, which lives on a
reference page. Cross-type links like these turn the four types,
explanation, how-to, reference, and SOP, into one connected system
instead of four separate silos.

## How consistency is enforced

These rules live in two places, not just this page. A project-scoped
Claude Code skill,
[`meridian-doc-standards`](https://github.com/anaysesardinha/portfolio/blob/main/.claude/skills/meridian-doc-standards/SKILL.md),
encodes them too.

I drafted every page in this sample with that skill active. The same
checklist ran every time. Nothing depended on memory from page to page.

The skill and this page state the same rules for different readers.
Claude Code follows the skill step by step while drafting a page. This
page explains the same rules, and why they exist, to a person.
