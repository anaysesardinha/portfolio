# Documentation Standards

This guide states the rules behind the [Meridian Contract Logistics
sample](/docs/meridian-logistics/about-this-sample) and why each rule
exists.

## Audience personas

The sample writes for three personas. The following table lists each
one, what they need from these docs, and their assumed technical
level:

| Persona | Role summary | Primary need from these docs | Technical level |
|---|---|---|---|
| Warehouse Operations | Front-line staff running receiving, storage, picking, and cycle counts | Exact, repeatable procedures: SOPs and how-to guides | Comfortable with Wayfinder WMS day to day; no assumed logistics jargon beyond terms each page defines in context |
| Account Managers / Client Services | Client-facing staff managing contracts, SLAs, and escalations | Context for client conversations: explanation pages | Familiar with contract and SLA terms; limited exposure to warehouse-floor procedures |
| New Hires | Staff onboarding into any of the above roles | Background before task instructions: explanation pages first, then how-to guides | Limited familiarity with Meridian-specific systems and terminology |

These personas map to three rules for writing content:

- Explanation pages assume a New Hire or Account Manager reading
  without prior context.
- How-to guides and SOPs assume a Warehouse Operations reader who
  already completed onboarding.
- Reference pages serve all three personas as lookup material for the
  Meridian operation itself, such as storage requirements or contact
  points, not as a starting point.

## Standards

The following sections group every rule behind this sample, and why it
exists, by what each one governs.

### Structure and metadata

Rules that keep every page's shape and frontmatter predictable:

| Rule | Why |
|---|---|
| Every page is exactly one Diataxis type: **explanation**, **how-to**, **reference**, or **SOP**. A page never mixes types. | Mixing types hides key details. A reader scanning a concept page for steps skips past them. A reader scanning a how-to guide for a definition misses it. |
| Every page carries a frontmatter schema, including `doc_type`, `owner`, `last_reviewed`, `review_cadence`, and `applies_to`. | Frontmatter lets tooling find overdue pages, page owners, and where a new hire should start reading. |
| The `owner` field always names a role, such as "Warehouse Operations Manager," never a person. | People change jobs. A role survives a reorg. A name doesn't. |
| Every non-SOP page opens with an Audience admonition. SOPs state audience through their **Applies to** line instead. | An SOP already states audience in **Applies to**. Repeating it would add nothing. |
| Every SOP follows the same template: Purpose, Prerequisites, Procedure, Troubleshooting, Related documents. | A fixed template removes a decision for new authors. It also speeds up an audit: every SOP puts each section in the same place. |
| **Owner**, **Last reviewed**, **Review cadence**, and **Applies to** each appear twice on an SOP: once in frontmatter, once in a table in the page body. | Frontmatter is what tooling reads. The table is what a person reads on the floor. |

### Writing

Rules that keep steps and prose consistent:

| Rule | Why |
|---|---|
| A numbered step holds one action. | Combining two actions into one step hides whether the reader completed both of them. |
| A step states the expected outcome when it is not obvious. | The reader needs to know the step worked before moving to the next one. |
| A warning appears immediately before the step it applies to, never after. | A warning that arrives after the step is too late to prevent the mistake. |
| Every page defines each domain term inline, in a short comma clause, the first time it appears. There is no shared glossary page to defer to. | A reader shouldn't have to leave the page they're using to understand a term. |

### Cross-linking

Rules that connect the four page types into one system:

| Rule | Why |
|---|---|
| Every page links to at least one related page, favoring links across Diataxis types over links within the same type. | Cross-type links turn the four types into one connected system instead of four separate silos. |
| Related links sit under a **Related** (or **Related documents**) heading. Each link carries one short line summarizing what that page covers, reusing that page's own frontmatter `description`. This rule applies site-wide, not only inside the sample. | A reader scanning for where to go next should know what's on the other side before they click. |

### Enforcement

Rules that keep every rule above from depending on memory:

| Rule | Why |
|---|---|
| These rules live on this page and in a Claude Code skill, [`meridian-doc-standards`](https://github.com/anaysesardinha/portfolio/blob/main/.claude/skills/meridian-doc-standards/SKILL.md). | The same checklist runs every time someone drafts a page, so nothing depends on memory from page to page. |
| A [`docs-standards` GitHub Actions job](https://github.com/anaysesardinha/portfolio/blob/main/.github/workflows/ci.yml) blocks a pull request if a page is missing a required frontmatter field, such as `owner` or `review_cadence`, breaks the SOP template, or has no link to another page. A separate `link-check` job blocks it on any broken internal link. | The skill helps at drafting time, but deadline pressure can still push someone to skip a rule that lives only in a skill or a person's memory. Deadline pressure can't push past a CI check that fails the build. |

## Templates

Every page starts with this frontmatter:

```yaml
---
title: "..."
description: "..."
sidebar_position: N
doc_type: explanation | how-to | reference | sop
audience: "Warehouse Operations, Client Services"
owner: "Warehouse Operations Manager"
last_reviewed: YYYY-MM-DD
review_cadence: Quarterly | Biannual
applies_to: "All Meridian fulfillment sites"
---
```

Every SOP follows this exact structure:

```markdown
# SOP-XXX: [Title]

| Field | Value |
|---|---|
| Owner | [Role, never a person's name] |
| Last reviewed | [Date] |
| Review cadence | [Quarterly / Biannual] |
| Applies to | [Which teams or sites] |

## Purpose
## Prerequisites
## Procedure
## Troubleshooting
## Related documents
```
