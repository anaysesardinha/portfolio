# Documentation Standards

:::info[Audience]
This page is for anyone evaluating the documentation standards behind
this sample, including hiring managers and other technical writers.
:::

This guide states the rules behind the [Meridian Contract Logistics
sample](/docs/meridian-logistics/about-this-sample) and why each rule
exists.

## Standards

The sections below group every rule behind this sample, and why it
exists, by what each one governs.

### Structure and metadata

Rules that keep every page's shape and frontmatter predictable:

| Rule | Why |
|---|---|
| Every page is exactly one Diataxis type: **explanation**, **how-to**, **reference**, or **SOP**. A page never mixes types. | Mixing types hides key details. Readers scanning a concept page for steps skip past one buried there. Readers scanning a how-to guide for steps miss a definition buried there. |
| Every page carries a frontmatter schema, including `doc_type`, `owner`, `last_reviewed`, `review_cadence`, and `applies_to`. | Frontmatter lets tooling query which pages are overdue for review, which team owns a page, and which pages a new hire should read first. |
| The `owner` field always names a role, such as "Warehouse Operations Manager," never a person. | People change jobs. A role survives a reorg. A named person goes stale once they leave that role. |
| Every non-SOP page opens with an Audience admonition. SOPs state audience through their **Applies to** line instead. | Stating audience twice on the same SOP page would repeat the same fact for no reason. |
| Every SOP follows the same template: Purpose, Prerequisites, Procedure, Troubleshooting, Related documents. | A fixed template removes a decision for new authors and speeds up an audit. Anyone can scan ten SOPs and know exactly where each section sits. |
| **Owner**, **Last reviewed**, **Review cadence**, and **Applies to** each appear twice on an SOP: once in frontmatter, once in a table in the page body. | Frontmatter is what tooling reads. The table is what a person reads on the floor, not the page's raw metadata. |

### Writing

Rules that keep steps and prose consistent:

| Rule | Why |
|---|---|
| A numbered step holds one action. | Combining two actions into one step hides whether the reader completed both of them. |
| A step states the expected outcome when it is not obvious. | The reader needs to know the step worked before moving to the next one. |
| A warning appears immediately before the step it applies to, never after. | A warning that arrives after the step is too late to prevent the mistake. |
| Every page defines each domain term inline, in a short comma clause, the first time it appears. There is no shared glossary page to defer to. | A reader shouldn't have to leave the page they're using to understand a term. |

### Cross-linking

Rules that connect the four page types into one system:

| Rule | Why |
|---|---|
| Every page links to at least one related page, favoring links across Diataxis types over links within the same type. | Cross-type links turn the four types into one connected system instead of four separate silos. |
| Related links sit under a **Related** (or **Related documents**) heading, as a bare list of link titles, with no sentence describing what each one covers. This rule applies site-wide, not only inside the sample. | A reader scanning for where to go next needs the link, not a summary of the destination. The summary already lives on that page. |

### Enforcement

Rules that keep every rule above from depending on memory:

| Rule | Why |
|---|---|
| These rules live on this page and in a Claude Code skill, [`meridian-doc-standards`](https://github.com/anaysesardinha/portfolio/blob/main/.claude/skills/meridian-doc-standards/SKILL.md). | The same checklist runs every time someone drafts a page, so nothing depends on memory from page to page. |
| A [`docs-standards` GitHub Actions job](https://github.com/anaysesardinha/portfolio/blob/main/.github/workflows/ci.yml) blocks a pull request if a page is missing a required frontmatter field, such as `owner` or `review_cadence`, breaks the SOP template, or has no link to another page. A separate `link-check` job blocks it on any broken internal link. | The skill helps at drafting time, but deadline pressure can still push someone to skip a rule that only lives in a skill or a person's memory. Deadline pressure cannot push past a CI check that fails the build. |

## Templates

These are the literal formats the standards above produce.

Every page carries this frontmatter:

```yaml
---
title: "..."
description: "..."
sidebar_position: N
doc_type: explanation | how-to | reference | sop
audience: "Warehouse Operations, Client Services"
owner: "Warehouse Operations Manager"
last_reviewed: YYYY-MM-DD
review_cadence: Quarterly | Biannual
applies_to: "All Meridian fulfillment sites"
---
```

Every non-SOP page opens with this admonition; fill it in for that
specific page:

```
:::info[Audience]
This page is for Warehouse Operations and Client Services teams.
:::
```

Every SOP follows this exact structure:

```markdown
# SOP-XXX: [Title]

| Field | Value |
|---|---|
| Owner | [Role, never a person's name] |
| Last reviewed | [Date] |
| Review cadence | [Quarterly / Biannual] |
| Applies to | [Which teams or sites] |

## Purpose
## Prerequisites
## Procedure
## Troubleshooting
## Related documents
```
