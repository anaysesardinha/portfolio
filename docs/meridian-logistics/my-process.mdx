# My Process

:::info[Audience]
This page is for anyone who wants to see the reasoning behind this
sample, not just the finished pages.
:::

[About this sample](/docs/meridian-logistics/about-this-sample) states
what this sample is. This page states why it looks the way it does.

## Starting from the audience, not the content

Before writing a single page, I defined three audiences (see [Audience
Personas](/docs/meridian-logistics/reference/audience-personas)):

- Warehouse Operations
- Account Managers and Client Services
- New hires

Each one needs something different from documentation:

- Operations staff need exact, repeatable procedures.
- Account managers need context for client conversations.
- New hires need background before either of those makes sense.

That split drove the information architecture. I chose it before writing
any page.

## Why Diataxis

Diataxis splits documentation into four types. Each type matches what
the reader is trying to do:

- Understand
- Act
- Look something up
- Follow a fixed procedure

Internal operational docs usually fail by mixing these. A procedure gets
buried inside conceptual asides a reader has to skip. A reference table
gets buried inside prose no one reads twice.

Enforcing one type per page removes that failure mode by construction. I
do not have to maintain the discipline by hand on every edit.

## Why one of each type, on one connected topic

An earlier version of this sample covered four SOPs, seven how-to guides,
and several unrelated explanation and reference pages.

I cut it down to four pages, all on one topic: inbound receiving and
put-away.

- One explanation page
- One how-to guide
- One reference page
- One SOP

Two problems drove that cut.

First, volume does not prove a template works. One fully realized SOP
proves it as well as four would. A hiring manager needs to see
consistency, not quantity.

Second, one shared topic lets a reader trace a real thread end to end:

- The explanation page sets up why receiving and storage work the way
  they do.
- The how-to guide handles the one failure mode that comes up during
  receiving.
- The reference page defines where received goods get stored.
- The SOP ties all of it into one procedure.

Four unrelated topics would have shown the same template four times,
with no depth on any one process.

The Glossary and Audience Personas pages stay in as supporting material.
They serve every topic, not just this one, so they do not count as
additional topic content.

## How the AI-assisted workflow fit in

I drafted this sample with Claude Code. A project-scoped skill,
[`meridian-doc-standards`](https://github.com/anaysesardinha/portfolio/blob/main/.claude/skills/meridian-doc-standards/SKILL.md),
backed every page.

The skill encodes three things as a checklist:

- The frontmatter schema
- The SOP template
- The cross-linking rule

I drafted every page in this sample against that checklist, including
the pages I later cut. The same checklist ran every time. Nothing
depended on memory from page to page. That is why the frontmatter fields
and the SOP structure stayed identical across the whole sample.

The repository's CI workflow builds the site and checks every link on
every push. It uses the same `onBrokenLinks: throw` setting that caught
broken cross-links locally while I wrote this sample. That check keeps
the no-orphan-pages rule true over time, not just on the day I wrote it.
